Chaque route authentifiée accepte un seul identifiant dans l'en-tête `Authorization` : une [clé API](/fr/pages/rest/api-keys), que vous créez une fois sur la page de votre compte, ou un **token de connexion**, que cet endpoint renvoie en échange de votre mot de passe. Si vous écrivez un programme, utilisez une clé et ignorez cette page ; la [vue d'ensemble de l'authentification](/fr/pages/authentication) compare les deux.

Un token de connexion est valide **30 jours**, après quoi il est remplacé sur place par rotation (voir [Rotation du token](#token-rotation)).

## Se connecter {#log-in}

`POST /user/login`

<CodeGroup>
```bash curl
curl -X POST https://api.4casters.io/user/login \
  -H "Content-Type: application/json" \
  -d '{"username": "your_username", "password": "your_password"}'
```

```json Corps JSON
{
  "username": "your_username",
  "password": "your_password"
}
```
</CodeGroup>

### Requête {#request}

<ParamField body="username" type="string" required>Nom d'utilisateur du compte (ou email).</ParamField>
<ParamField body="password" type="string" required>Mot de passe du compte.</ParamField>

### Réponse {#response}

Le token est renvoyé à la fois dans `data.user.auth` **et** dans un cookie signé `auth` (`Set-Cookie`). Pour la plupart des intégrations côté serveur, vous voudrez capturer `data.user.auth` et ignorer le cookie.

```json
{
  "data": {
    "user": {
      "id": "5fe37acbb5a23600123662c1",
      "username": "your_username",
      "auth": "5cd551d6...",
      "type": "p2p",
      "oddsFormat": "american",
      "displayBalance": 1250.50,
      "creditLimit": 500,
      "liability": -125.00,
      "commissionCharged": 0.01,
      "hasMarketMakerAccess": false,
      "isPro": false,
      "createdAt": "2020-12-23T17:14:09.000Z"
    }
  }
}
```

Voir [`User`](/api-reference/openapi.json) dans le schéma OpenAPI pour la liste complète des champs.

### Réponses d'erreur {#error-responses}

| Statut | Signification |
| ------ | ------- |
| `400`  | `username` et `password` sont requis. |
| `401`  | Nom d'utilisateur ou mot de passe incorrect. |
| `403`  | Compte banni, verrouillé, fermé ou gelé. |
| `429`  | Limite de débit de connexion dépassée. |

## Autoriser les requêtes {#authorizing-requests}

Passez le token de `data.user.auth` sur chaque requête suivante. Une clé API se place exactement au même endroit. Trois formats d'en-tête / de payload sont acceptés, dans cet ordre de préférence :

<Tabs>
  <Tab title="En-tête Authorization (recommandé)">
    ```bash
    curl https://api.4casters.io/user/getMe \
      -H "Authorization: Bearer 5cd551d6..."
    ```
    Le préfixe `Bearer ` est optionnel — passer le token nu fonctionne aussi.
  </Tab>
  <Tab title="Cookie">
    Le cookie signé `auth` posé par `/user/login` est honoré automatiquement sur chaque endpoint quand il est réutilisé sur le même client.
  </Tab>
  <Tab title="Champ du corps (POST uniquement)">
    ```json
    { "token": "5cd551d6...", "...": "..." }
    ```
    Fourni comme solution de repli pour les clients qui ne peuvent pas facilement définir des en-têtes personnalisés (par ex. certains émetteurs de webhooks).
  </Tab>
</Tabs>

Si aucun identifiant n'est fourni, ou s'il est inconnu, révoqué ou expiré, le serveur répond `401 InvalidCredentials` (une clé API expirée renvoie `401 ApiKeyExpired`). Un identifiant refusé en raison de la provenance de la requête, ou pour un compte gelé, donne un `403` ; la [page Clés API](/fr/pages/rest/api-keys#responses) liste tous les messages.

## Rotation du token {#token-rotation}

Les requêtes authentifiées avec des tokens de plus de 30 jours obtiennent automatiquement un nouveau token par rotation. Quand cela se produit, le nouveau token est renvoyé dans l'en-tête de réponse `X-Auth-Token` (et dans un cookie signé `auth` mis à jour). L'ancien token cesse immédiatement de fonctionner ; la requête qui a déclenché la rotation réussit quand même, mais toute requête ultérieure avec l'ancienne valeur renvoie `401`. Les intégrations de longue durée doivent surveiller cet en-tête et persister la nouvelle valeur, ou simplement se reconnecter à chaque `401`.

## Se déconnecter {#logging-out}

`POST /user/logout` invalide le token utilisé pour l'appel. Les requêtes suivantes avec ce token renvoient `401` ; les autres tokens détenus pour le même compte, ainsi que les clés API, ne sont pas affectés. La déconnexion exige un token de connexion ; une clé est refusée ici avec `403 LoginSessionRequired`.

## Authentification à deux facteurs {#two-factor-authentication}

L'authentification à deux facteurs protège les retraits, pas la connexion. `POST /user/login` n'exige jamais de code, quel que soit le réglage 2FA du compte.
