O feed de utilizador transmite as atualizações do âmbito da sua conta (ordens, execuções, cancelamentos).

<CodeGroup>
```javascript JavaScript
// user_feed_quickstart.js 
const WebSocket = require('ws'); 
const token = process.env.FOURCASTERS_TOKEN; 
function connectUserFeed() { 
  const ws = new WebSocket('wss://streaming-api.4casters.io/v2/user', { 
    headers: { Authorization: token }, 
  });
  let pingTimer; let lastPong = Date.now(); 
  ws.on('open', () => { 
    console.log('user feed connected'); 
    pingTimer = setInterval(() => { 
      if (ws.readyState === WebSocket.OPEN) { 
        ws.ping(); 
      } 
      if (Date.now() - lastPong > 30000) { 
        console.warn('user feed: missed pong >30s, closing'); 
        ws.terminate(); 
      } 
    }, 10000); 
  }); 
 
  ws.on('pong', () => { lastPong = Date.now(); }); 
 
  ws.on('message', (buf) => { 
    try { 
      const msg = JSON.parse(buf.toString()); 
      console.log('user update:', JSON.stringify(msg, null, 2)); 
    } catch { console.log('user update (raw):', buf.toString()); } 
  }); 
 
  ws.on('error', (e) => console.error('⚠️ user feed error:', e.message));
 
  ws.on('close', (code, reason) => { 
    console.log(`user feed closed: ${code} ${reason}`); 
    clearInterval(pingTimer); 
    // basic backoff reconnect 
    setTimeout(connectUserFeed, 1000); 
  }); 
} 
 
connectUserFeed(); 
```
</CodeGroup>

## Mensagens {#messages}

O feed de utilizador envia cada atualização como um **objeto JSON simples** (sem envelope de tuplo). Todas as atualizações partilham um envelope; a ação é determinada por quais de `unmatched` / `matched` estão preenchidos e por `origin`.

### Envelope comum {#common-envelope}

<CodeGroup>
```typescript Esquema
{
  matched:    null | MatchedBlock,
  unmatched:  null | UnmatchedBlock,
  origin:     "offer" | "wager",

  gameID:             string,
  parentGameID:       string | null,
  eventName:          string,
  league:             string,
  sport:              string,
  live:               boolean,
  start:              string,   // RFC3339
  awayRotationNumber: string,

  platform:           string,   // e.g. "api"
  createdAt:          string,   // RFC3339
  messageID:          string,   // Redis stream entry id, e.g. "1715361234567-0"
}
```
</CodeGroup>

`messageID` é o id de entrada do stream adicionado pela streaming-api antes do envio. Persista o último que processou — é o seu cursor de replay. Consulte [Reproduzir mensagens perdidas](#replaying-missed-messages) abaixo.

### O bloco `matched` {#the-matched-block}

Presente sempre que a atualização representa uma execução (`matched != null`). Todos os campos abaixo são enviados em
cada execução, salvo indicação de condicional. Todos os valores são da **sua** perspetiva — como taker vê
o lado que tomou, como maker vê o lado que publicou.

| Campo | Tipo | Enviado | Significado |
|---|---|---|---|
| `txID` | string | sempre | Id da aposta. Deduplique execuções por este campo — é o mesmo `txID` devolvido por [obter apostas correspondidas](/pt/pages/rest/user/get-matched-bets). |
| `orderID` | string | sempre | Id da ordem de onde saiu esta execução. Como maker, a sua ordem em espera; como taker, a ordem que atacou. |
| `wagerRequestID` | string | sempre | Id do pedido de colocação por detrás da execução. Como taker, o seu próprio pedido; como maker, o pedido que originalmente publicou a sua ordem. |
| `amount` | number | sempre | Montante **excluindo** a comissão. Igual a `risk` numa execução de maker, mas **não** numa execução de taker — ver abaixo. |
| `risk` | number | sempre | O que pode perder nesta execução. Como taker, inclui a comissão cobrada numa perda; como maker, não se aplica comissão. |
| `win` | number | sempre | O que pode ganhar nesta execução. Como taker, líquido da comissão cobrada num ganho; como maker, não se aplica comissão. |
| `odds` | integer | sempre | Odds americanas do seu lado da execução. |
| `type` | string | sempre | `moneyline`, `spread`, `total` ou `moneyline1x2`. |
| `side` | string | sempre | Consulte [semântica de side e market](#side-and-market-semantics-by-bet-type). |
| `number` | number | condicional | A linha de spread ou de total. Totalmente omitido em `moneyline` e `moneyline1x2`. |
| `market` | string | condicional | Apenas `moneyline1x2`. |
| `userReference` | string \| null | sempre | Devolve o `userReference` que enviou na ordem. `null` se não enviou nenhum. |
| `isPostArb` | boolean | condicional | `true` em execuções de ordens `postArb`; omitido caso contrário. |

<Warning>
  **Não derive `win` a partir de `risk`.** `risk` e `win` são arredondados a 2 casas decimais, cada um independentemente a partir
  do montante não arredondado, pelo que `risk x odds` pode divergir de `win` por um cêntimo. Registe o valor de `win` tal como
  é enviado; se estiver em falta, trate a mensagem como malformada em vez de a reconstruir.

  **Não trate `amount` como sinónimo de `risk`.** Numa execução de taker, `amount` exclui a
  comissão cobrada numa perda e `risk` inclui-a. Registar `amount` como o seu risco irá
  subcontabilizar a comissão em cada take.
</Warning>

<Note>
  As mesmas quantidades via REST ([obter apostas correspondidas](/pt/pages/rest/user/get-matched-bets)) são
  formatadas como cadeias com 2 casas decimais em vez de números, e são calculadas com uma ordem de
  comissão e arredondamento ligeiramente diferente. Reconcilie com um cêntimo de tolerância em vez de igualdade exata.
</Note>

### O bloco `unmatched` {#the-unmatched-block}

Presente sempre que a atualização diz respeito a uma ordem em espera no livro (ou a sair dele) — colocações,
cancelamentos e o lado maker de uma execução. As odds e os lados são da perspetiva do **maker**,
ou seja, o que você publicou, não o que o livro oferece aos outros.

| Campo | Tipo | Enviado | Significado |
|---|---|---|---|
| `orderID` | string | sempre | Id da ordem. |
| `wagerRequestID` | string | sempre | Id do pedido de colocação que criou a ordem. |
| `filled` | number | sempre | **Numa execução: o risco correspondido apenas por este evento**, não o total acumulado. `0` numa colocação. Num cancelamento é, em vez disso, o risco acumulado correspondido antes de o cancelamento chegar. |
| `offered` | number | sempre | Risco total que a ordem ofereceu. `0` identifica um cancelamento. |
| `remaining` | number | sempre | Risco ainda em espera no livro. `0` significa totalmente correspondida. |
| `odds` | integer | sempre | Odds americanas do seu lado da ordem. |
| `type` | string | sempre | `moneyline`, `spread`, `total` ou `moneyline1x2`. |
| `side` | string | sempre | Consulte [semântica de side e market](#side-and-market-semantics-by-bet-type). |
| `number` | number | condicional | A linha de spread ou de total. Totalmente omitido em `moneyline` e `moneyline1x2`. |
| `market` | string | condicional | Apenas `moneyline1x2`. |
| `userReference` | string | condicional | Devolve o `userReference` que enviou; omitido se a ordem não trazia nenhum. |
| `isPostArb` | boolean | condicional | `true` para ordens `postArb`; omitido caso contrário. |

<Warning>
  `filled` e `remaining` não são o mesmo tipo de número. `remaining` é estado corrente — o que
  resta no livro neste momento — mas numa execução `filled` descreve apenas esse evento. Ao longo de várias
  execuções parciais, não somam: `filled + remaining` é igual a `offered` na primeira execução e
  diverge a partir daí.

  Para acompanhar quanto de uma ordem em espera já foi correspondido, use `offered - remaining`, ou acumule
  `filled` você mesmo. Não misture os dois.
</Warning>

### Como identificar a ação {#how-to-identify-the-action}

- `unmatched.filled === 0 && unmatched.offered > 0` -> ordem colocada
- `unmatched.offered === 0` -> ordem cancelada
- `matched != null && unmatched == null` -> correspondida como taker
- `matched != null && unmatched != null` -> correspondida como maker (execução parcial se `unmatched.remaining > 0`)

As atualizações de ordens colocadas com `orderType: "postArb"` também trazem `isPostArb: true` dentro de `matched` / `unmatched` (nas atualizações de colocada, executada e cancelada); o campo é omitido caso contrário.

### Semântica de side e market por tipo de aposta {#side-and-market-semantics-by-bet-type}

O significado de `side` (e quais os campos extra que aparecem) dentro de `matched` / `unmatched` depende de `type`:

| `type` | `side` | `number` | `market` |
|---|---|---|---|
| `moneyline` | hex de ObjectID do participante | — | — |
| `spread` | hex de ObjectID do participante | linha de spread (p. ex. `6.5`) | — |
| `total` | `"over"` / `"under"` | linha de total (p. ex. `209.5`) | — |
| `moneyline1x2` | `"yes"` / `"no"` | — | hex de ObjectID do participante (casa ou fora) ou `"draw"` |

`market` só está presente em atualizações de `moneyline1x2`: indica o resultado de 3 vias a que o mercado diz respeito (equipa da casa, equipa de fora ou o empate), e `side` diz se a aposta é yes ou no sobre esse resultado. Todos os campos são da **sua** perspetiva — como maker vê o lado que publicou; como taker vê o lado que tomou.

## Reproduzir mensagens perdidas {#replaying-missed-messages}

O feed de utilizador v2 suporta **recuperação de lacunas após uma ligação perdida**. Cada mensagem traz um `messageID` (um id de entrada de stream monotonicamente crescente, p. ex. `"1751552702114-0"`). Se a sua ligação cair, pode obter exatamente as mensagens que perdeu.

### Endpoint {#endpoint}

```
GET https://streaming-api.4casters.io/v2/user/messages?afterID=<messageID>&beforeID=<messageID>
```

A autenticação é a mesma do WebSocket: token no cabeçalho `Authorization`, no cabeçalho `Auth` ou no parâmetro de consulta `token`. Só são devolvidas as mensagens pertencentes ao utilizador autenticado.

| Parâmetro | Obrigatório | Significado |
|---|---|---|
| `afterID` | sim | O `messageID` da **última mensagem que processou** antes da queda. Os resultados começam estritamente depois dele. |
| `beforeID` | não | Limite superior exclusivo. Omita para ler até ao fim do histórico retido. |

### Resposta: `success` {#response-success}

O seu `afterID` ainda estava presente no histórico retido, pelo que a lista devolvida é um preenchimento de lacuna **completo** — nada entre `afterID` e `beforeID` se perdeu:

```json
{
  "status": "success",
  "messages": [
    { "...": "feed messages in order, each with its messageID" }
  ]
}
```

Aplique as mensagens por ordem e retome o processamento das mensagens ao vivo.

### Resposta: `cache_expired` {#response-cache_expired}

O seu `afterID` já saiu do histórico retido, pelo que o servidor **não consegue provar que o replay está completo**:

```json
{
  "status": "cache_expired",
  "availableMessages": [
    { "...": "whatever is still retained, oldest first" }
  ]
}
```

`availableMessages` é o que ainda está retido, do mais antigo para o mais recente. As mensagens mais antigas do que a janela de retenção não são recuperáveis através de replay — religue prontamente em vez de confiar num look-back longo.

### Exemplo: cliente com religação e replay {#example-reconnecting-client-with-replay}

Um cliente Node.js completo (ping/pong de keepalive omitido por brevidade — veja o quickstart no topo desta página). Duas coisas o mantêm correto: cada mensagem — ao vivo, em buffer ou reproduzida — passa por uma única verificação de cursor que só avança, e um replay falhado religa em vez de passar a ao vivo por cima da lacuna.

<CodeGroup>
```javascript JavaScript
// user_feed_replay_client.js
const WebSocket = require('ws');
const token = process.env.FOURCASTERS_TOKEN;
const HOST = 'streaming-api.4casters.io';

// Your replay cursor: the messageID of the last message you processed.
// Persist it durably (disk/db) so replay also works across process restarts.
let cursor = null;

// messageIDs are "<unix-ms>-<seq>"; compare numerically part by part.
function isAfterCursor(messageID) {
  if (!cursor) return true;
  const [ms, seq] = messageID.split('-').map(Number);
  const [cMs, cSeq] = cursor.split('-').map(Number);
  return ms > cMs || (ms === cMs && seq > cSeq);
}

function processMessage(msg) {
  // Replay can overlap live delivery, so every message — live, buffered,
  // or replayed — passes through this check. The cursor only moves forward.
  if (!isAfterCursor(msg.messageID)) return;
  cursor = msg.messageID;
  // Business logic goes here. `msg` is the same envelope everywhere.
  console.log('user update:', msg.origin, msg.messageID);
}

async function replayGap() {
  const params = new URLSearchParams({ afterID: cursor });
  const res = await fetch(`https://${HOST}/v2/user/messages?${params}`, {
    headers: { Authorization: token },
  });
  if (!res.ok) throw new Error(`replay request failed: ${res.status}`);
  const body = await res.json();

  if (body.status === 'success') {
    // Complete gap-fill: nothing between the cursor and now was lost.
    body.messages.forEach(processMessage);
  } else if (body.status === 'cache_expired') {
    // Apply what is still retained; anything older is not recoverable.
    console.warn('replay window expired - messages may have been lost');
    body.availableMessages.forEach(processMessage);
  } else {
    throw new Error(`unexpected replay status: ${body.status}`);
  }
}

function connect() {
  const ws = new WebSocket(`wss://${HOST}/v2/user`, {
    headers: { Authorization: token },
  });

  let live = false; // false while replay is in flight
  const buffer = [];
  // Settles when the open handler is done, so a reconnect never starts a
  // second replay while this one is in flight.
  let openTask = Promise.resolve();

  ws.on('open', () => {
    openTask = (async () => {
      console.log('user feed connected');
      if (cursor !== null) {
        try {
          await replayGap();
        } catch (e) {
          // Going live now would advance the cursor over the unfilled gap
          // and lose it — reconnect and retry from the same cursor.
          console.error('replay failed, reconnecting:', e.message);
          ws.terminate();
          return;
        }
      }
      // Drain messages buffered during replay; processMessage skips
      // anything the replay already covered.
      buffer.splice(0).forEach(processMessage);
      live = true;
    })();
  });

  ws.on('message', (buf) => {
    const msg = JSON.parse(buf.toString());
    if (live) processMessage(msg);
    else buffer.push(msg);
  });

  ws.on('close', async (code, reason) => {
    console.log(`user feed closed: ${code} ${reason} - reconnecting`);
    await openTask.catch(() => {});
    setTimeout(connect, 1000);
  });

  ws.on('error', (e) => console.error('user feed error:', e.message));
}

connect();
```
</CodeGroup>
