Every 4casters API, REST and WebSocket alike, authenticates the same way: one credential string in the `Authorization` header. There are two kinds of credential, and the only decision is which one to use.

| | API key | Login token |
| --- | --- | --- |
| **Made for** | Programs: bots, scripts, backend jobs. | The website and anything short-lived. |
| **How you get it** | Once, from your account page. | `POST /user/login` with your username and password. |
| **Lifetime** | Until you revoke it, or an expiry you chose when creating it. | 30 days, then rotated in place on the next request. |
| **Network restriction** | Per key: IPv4 and IPv6 addresses or CIDR ranges. | None (an account-wide whitelist can be arranged through support). |
| **Revocation** | Per key, instant, from the account page. | Logout, or a password change, revokes every login token. |
| **Can manage the account** | No. Account administration (keys, password, 2FA, withdrawals) needs a website session. | Yes. |

**If you are writing code that runs unattended, use an API key.** Login tokens exist so the website can sign you in; they rotate, they die with a password change, and a leaked one is as good as your password until you notice.

## API keys

Create one at **My Account → Security → API Keys** (or go straight to [4casters.io/account/api-keys](https://4casters.io/account/api-keys)): name it, optionally restrict it to your servers' IP ranges and give it an expiry, and copy the key from the confirmation. It is shown once.

A key looks like `4ck_Wk15VXFX_T4MPcp8Ij2IODI7OFFIlQsHmvvzJ3Nj8C-StfVe3h0k`. The first part, `4ck_Wk15VXFX`, is its **Key ID**: not secret, and how the account page refers to the key. The rest is the secret.

Send it exactly where a login token goes:

<Tabs>
  <Tab title="REST API">
    ```bash
    curl https://api.4casters.io/user/getMe \
      -H "Authorization: 4ck_Wk15VXFX_T4MPcp8Ij2IODI7OFFIlQsHmvvzJ3Nj8C-StfVe3h0k"
    ```
  </Tab>
  <Tab title="Orders WebSocket">
    ```javascript
    const ws = new WebSocket('wss://orders-api.4casters.io/orders/ws', {
      headers: { Authorization: process.env.FOURCASTERS_API_KEY },
    });
    ```
  </Tab>
  <Tab title="Streaming WebSocket">
    ```javascript
    const ws = new WebSocket('wss://streaming-api.4casters.io/v2/user', {
      headers: { Authorization: process.env.FOURCASTERS_API_KEY },
    });
    ```
  </Tab>
</Tabs>

There is no login step and nothing to refresh. The full reference, including allowed IPs, expiry, what a key cannot do, and every error it can produce, is on the [API keys page](/pages/rest/api-keys).

## Login tokens

A login token is what the website holds after you sign in. It works on every API, so it is fine for a quick experiment or a one-off script; for anything that keeps running, prefer a key.

### 1. Log in

`POST https://api.4casters.io/user/login`

<CodeGroup>
```bash curl
curl -X POST https://api.4casters.io/user/login \
  -H "Content-Type: application/json" \
  -d '{"username": "your_username", "password": "your_password"}'
```

```javascript JavaScript
const res = await fetch('https://api.4casters.io/user/login', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    username: process.env.FOURCASTERS_USERNAME,
    password: process.env.FOURCASTERS_PASSWORD,
  }),
});
const { data } = await res.json();
const token = data.user.auth;
```

```python Python
import os, requests

res = requests.post(
    "https://api.4casters.io/user/login",
    json={
        "username": os.environ["FOURCASTERS_USERNAME"],
        "password": os.environ["FOURCASTERS_PASSWORD"],
    },
    headers={"User-Agent": "my-bot/1.0"},
)
token = res.json()["data"]["user"]["auth"]
```
</CodeGroup>

The `username` field accepts either your username or the email on the account.

The token is at `data.user.auth` in the response body: a 256-character hex string. The same value is also set as a signed `auth` cookie; server-side integrations should capture `data.user.auth` and ignore the cookie.

```json
{
  "data": {
    "user": {
      "id": "5fe37acbb5a23600123662c1",
      "username": "your_username",
      "auth": "5cd551d6...",
      "...": "..."
    }
  }
}
```

The full response shape is documented on the [REST login page](/pages/rest/authentication).

<Tip>
Log in **once** and reuse the token. Login is rate-limited per IP and per account, and every successful login mints a new token. Logging in again does not invalidate tokens you already hold.
</Tip>

### 2. Send the token

<Tabs>
  <Tab title="REST API">
    Pass the token in the `Authorization` header. The `Bearer ` prefix is optional.

    ```bash
    curl https://api.4casters.io/user/getMe \
      -H "Authorization: Bearer 5cd551d6..."
    ```

    A missing, unknown, or expired token returns `401` with body `{ "error": { "message": "InvalidCredentials", "code": 401 } }`.
  </Tab>
  <Tab title="Orders WebSocket">
    Pass the token in the `Authorization` header on the handshake. The server derives your account from the token.

    ```javascript
    const ws = new WebSocket('wss://orders-api.4casters.io/orders/ws', {
      headers: { Authorization: token },
    });
    ```

    See [Orders API](/pages/websocket/introduction).
  </Tab>
  <Tab title="Streaming WebSocket">
    Same header, same token, for both the user feed and the price feed.

    ```javascript
    const ws = new WebSocket('wss://streaming-api.4casters.io/v2/user', {
      headers: { Authorization: token },
    });
    ```

    See [Streaming API](/pages/streaming/introduction).
  </Tab>
</Tabs>

### Token lifetime

| | |
| --- | --- |
| **Valid for** | 30 days from login. |
| **After 30 days** | The next authenticated REST request rotates the token in place: the old value stops working immediately and the replacement is returned in the `X-Auth-Token` response header. |
| **Logout** | `POST /user/logout` invalidates the token used to make that call. Other tokens for the account are unaffected. |
| **Password change** | Invalidates every login token on the account. API keys are not affected. |

If you must run on a login token for more than a month, do one of the following:

- **Re-login on any `401`.** Simplest and robust. Treat `401` as "get a fresh token", not as a fatal error.
- **Watch for `X-Auth-Token`.** Whenever that header is present on a response, persist its value and use it from then on.

A script that logs in once, stores the token, and never looks at response headers will work for exactly 30 days and then fail with `401` on every request. An API key has none of this.

### Login errors

| Status | Meaning | What to do |
| --- | --- | --- |
| `400` | `username` or `password` missing from the body. | Send both as JSON. |
| `401` | Username or password is incorrect. | Check the credentials. The message is the same whether the account exists or not. |
| `403` | Account banned, closed, or frozen. | Contact support. |
| `428` | `CHALLENGE_REQUIRED`. Only returned while the platform is actively mitigating a credential-stuffing attack; a human-verification challenge is being demanded. | Keep using a credential you already hold, or wait and retry. Scripted clients cannot solve the challenge. An API key is never challenged. |
| `429` | Login rate limit exceeded. | Back off for the `Retry-After` seconds and reuse existing tokens instead of re-logging in. |

## Two-factor authentication

Two-factor authentication on 4casters protects **withdrawals**, not login. Enabling it on your account does not change how you authenticate against the API: `POST /user/login` never asks for a code, and API keys are unaffected.

## Keeping credentials safe

- Store keys, usernames and passwords in environment variables or a secrets manager, never in source control.
- Treat a key or a token like a password. Anyone holding it can place orders and read your account.
- Give each program its own API key, named after the program, and restrict it to the addresses it runs from. If one leaks, revoke that one.
- Consider a dedicated account for automated trading so a leaked credential does not expose your main balance. Accounts are opened the same way as any user account.
