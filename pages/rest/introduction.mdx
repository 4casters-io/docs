The 4casters REST API lets you log in, query games and the orderbook, place / edit / cancel orders, and read your bet history programmatically. It is the same API that powers the 4casters web app.

## Base URL

All endpoints in this section are rooted at:

```
https://api.4casters.io
```

## Conventions

- **Transport**: HTTPS only.
- **Encoding**: JSON. Send `Content-Type: application/json` on every request that has a body.
- **Response envelope**: With a couple of well-marked exceptions (`/affiliate/getAffiliateCommission`, `/exchange/getOddsForAveragePrice`), every successful response is wrapped: `{ "data": <payload> }`.
- **Identifiers**: Game ids, participant ids, and order ids are MongoDB `ObjectID` strings (24-character hex).
- **Odds**: All odds are American format (negative for favorites, positive for underdogs) unless noted otherwise.
- **Time**: All timestamps are ISO 8601 with `Z` (UTC).

## Authentication

Almost every endpoint requires authentication. Log in once via [POST `/user/login`](/pages/rest/authentication), then send the returned auth token on every request — see [Authentication](/pages/rest/authentication) for details.

## Per-order errors vs HTTP errors

The "place" and "edit" endpoints accept batches and return per-order results. A successful HTTP `200` response can still contain individual order failures inside `data.createdSessions[i]`. See the per-order error shape on each endpoint page.

HTTP-level errors (`4xx`, `5xx`) are returned as `{ "error": "<message>" }`.

## Rate limiting

### Orders, per account

Placing orders is limited per account. REST and the [Orders API WebSocket](/pages/websocket/introduction) share one budget.

<Note>
Limits are measured since 2026-10-26 and enforced from **Monday, 2026-11-02**.
</Note>

| Tier | Burst | Sustained |
|---|---|---|
| Standard | 200 orders | 20 / second |
| Market maker | 2,000 orders | 150 / second |

- Each order counts. A batch of 50 uses 50.
- An idle account can place its burst at once, then its sustained rate. Capacity refills continuously.
- A batch that doesn't fit is rejected whole and uses nothing.
- Batches are capped at 1,000 orders.
- Cancels, edits and replaces never count.

Market-maker limits are set per account. Contact support to request them.

[Cancel by reference](/pages/rest/orders/cancel-by-reference) and `pauseOrders` go through a per-account queue: 15 cancels / second, `429` when 50 are queued, and `423` while a cancel-all runs. Other cancels skip it.

#### Over the limit

- **REST:** `429` with `Retry-After` (seconds):

```json
{
  "error": {
    "message": "rate limited",
    "code": 429,
    "details": { "code": "rate_limited", "retryAfterMs": 350, "retryAfterSeconds": 1 }
  }
}
```

- **WebSocket:** `error_type` `rate_limited` with `retryAfterMs`. The connection stays open. See [Place order errors](/pages/websocket/place-order#error-responses).

`retryAfterMs` is the wait until the batch fits. `-1` means it never will, so split it. Rejected requests are not processed, so resending is safe.

### Per IP (REST)

Every REST request counts, cancels included:

| Limit | Over it |
|---|---|
| 1,000 requests / 10 seconds | `429` until the window ends |
| 30,000 requests / 10 minutes | IP blocked 10 minutes, doubling on each repeat within 24 hours, up to 24 hours |

Both return `429` with `Retry-After` and `{ "error": "Too many requests. Please try again later." }`. Retrying during a block doesn't shorten it.

WebSocket messages don't count, so high-frequency clients should use the [Orders API WebSocket](/pages/websocket/introduction).

### Authentication

Login, password reset and signup have extra throttling.

Read endpoints have only the per-IP limit.

## Timeouts

Requests that take longer than **15 seconds** server-side are aborted and return `503` with body `{ "error": { "message": "Network Error", "code": 503 } }`.

## Real-time updates

The REST API pairs with the [WebSocket Streaming API](/pages/streaming/introduction) for real-time orderbook ticks and per-account fill / settle events. The auth token returned by `/user/login` works for both.
