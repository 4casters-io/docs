The score feed streams live game state — score, period, clock, and the detail that matters for each sport — as JSON messages over a raw WebSocket connection.

<CodeGroup>
```javascript JavaScript
// score_feed_quickstart.js
const WebSocket = require('ws');
const token = process.env.FOURCASTERS_TOKEN;

function connectScoreFeed() {
  const ws = new WebSocket('wss://streaming-api.4casters.io/v1/score', {
    headers: { Authorization: token },
  });

  let pingTimer; let lastPong = Date.now();

  ws.on('open', () => {
    console.log('score feed connected');

    // Optional: narrow the feed to specific games / leagues / sports.
    // Omit this block to receive every live game (default).
    ws.send(JSON.stringify({
      type: 'subscribe',
      gameIDs: [],
      leagueIDs: ['NBA'],
      sportIDs: [],
      replace: true,
    }));

    pingTimer = setInterval(() => {
      if (ws.readyState === WebSocket.OPEN) ws.ping();
      if (Date.now() - lastPong > 30000) {
        console.warn('score feed: missed pong >30s, closing');
        ws.terminate();
      }
    }, 10000);
  });

  ws.on('pong', () => { lastPong = Date.now(); });

  ws.on('message', (buf) => {
    try {
      const [type, payload] = JSON.parse(buf.toString());
      if (type !== 'gameState') return; // ignore types you don't know
      console.log('game state:', JSON.stringify(payload, null, 2));
    } catch { console.log('score feed (raw):', buf.toString()); }
  });

  ws.on('error', (e) => console.error('score feed error:', e.message));

  ws.on('close', (code, reason) => {
    console.log(`score feed closed: ${code} ${reason}`);
    clearInterval(pingTimer);
    setTimeout(connectScoreFeed, 1000);
  });
}
connectScoreFeed();
```
</CodeGroup>

## Ping/Pong

The score feed supports standard WebSocket `ping/pong`. You may proactively `ping()` on an interval and track `pong` to verify liveness.

## Snapshot on connect

When you connect, the feed sends the current state of every live game you are subscribed to **before** any live updates. Each snapshot message carries `"snapshot": true`.

This exists because the feed publishes **changes**, not a heartbeat. Without a snapshot, a client that connects at half time would know nothing about a game until it next moved — which can be many minutes.

- Snapshot messages use the same `[type, payload]` shape as live ones. The only difference is the `snapshot` flag.
- Games that have finished are not included.
- After the snapshot, live updates follow on the same socket. There is no separate "snapshot complete" message: treat each message the same way whether or not it is flagged.
- If you reconnect, you get a fresh snapshot. Rebuilding from it is the supported way to recover from a dropped connection.

## Subscriptions

By default a connected client receives every live game across all sports and leagues. To narrow the feed, send one of the following commands as a JSON text frame after the socket is `open`. Commands take effect for the lifetime of the connection.

Subscriptions use the same commands and the same keys as the [price feed](/pages/streaming/price-feed#subscriptions), so a client that already speaks to that feed needs no new concepts.

### Subscribe by gameID, league, or sport

Install a filter. `gameIDs` are 24-character Mongo ObjectID hex strings; `leagueIDs` are short codes like `NBA` / `MLB` / `EPL`; `sportIDs` are lowercase tokens like `basketball` / `baseball` / `soccer`.

<CodeGroup>
```json Replace (recommended)
{
  "type": "subscribe",
  "gameIDs": ["62619dce25e2fb049a71cc2e"],
  "leagueIDs": ["NBA"],
  "sportIDs": [],
  "replace": true
}
```
```json Additive
{
  "type": "subscribe",
  "gameIDs": [],
  "leagueIDs": ["MLB"],
  "sportIDs": [],
  "replace": false
}
```
</CodeGroup>

- `replace: true` clears any existing subscriptions on this connection and installs the new lists. Switches the connection into filtered mode.
- `replace: false` adds the new keys to whatever the connection is already subscribed to.

A `replace: true` subscribe also triggers a fresh snapshot for the games you just subscribed to, so narrowing the feed fills your new cards immediately rather than on their next change.

### Unsubscribe

Remove specific keys. The connection stays in its current mode (filtered or subscribe-all).

<CodeGroup>
```json JSON
{
  "type": "unsubscribe",
  "gameIDs": [],
  "leagueIDs": ["MLB"],
  "sportIDs": []
}
```
</CodeGroup>

### Subscribe to everything

Explicit catch-all. Clears any per-key subscriptions on the connection.

<CodeGroup>
```json JSON
{ "type": "subscribeAll" }
```
</CodeGroup>

### Routing semantics

- A `gameID` subscription also receives updates for child games whose `parentGameID` matches, so subscribing to a pre-match game also follows its live market.
- League IDs are case-insensitive — `mlb` and `MLB` are equivalent.
- Sport IDs are case-insensitive — `baseball` and `Baseball` are equivalent.
- Empty strings inside the arrays are ignored.
- `subscribe` with `replace: false` **and** all-empty arrays is a no-op.
- `subscribe` with `replace: true` **and** all-empty arrays is the "clear all my subs" path — the connection enters filtered mode with zero subscriptions and receives nothing until you subscribe again or send `subscribeAll`.

## Messages

Every message on `/v1/score` arrives as a 2-tuple `[type, payload]`.

**Ignore message types you do not recognise.** New types will be added to this feed without a version change; a client that assumes a fixed set will break when one arrives. Switch on `type` and skip the default case.

### `gameState`

Emitted whenever a game's observed state changes. One message per game per change — the feed does not repeat an unchanged state, so a quiet game is normal and is not a sign of a dead connection.

<CodeGroup>
```json JSON
[
  "gameState",
  {
    "gameID": "62619dce25e2fb049a71cc2e",
    "parentGameID": null,
    "league": "NBA",
    "sport": "basketball",
    "status": "LIVE",
    "detail": "6:12 - 3rd",
    "period": 3,
    "clock": "6:12",
    "clockSeconds": 372,
    "homeScore": 78,
    "awayScore": 71,
    "stoppage": null,
    "ts": 1791830400000
  }
]
```
</CodeGroup>

| Field | Type | Notes |
| --- | --- | --- |
| `gameID` | string | 24-character ObjectID hex |
| `parentGameID` | string or null | set on a live child game; **nullable** |
| `league` | string | short code, e.g. `NBA` |
| `sport` | string | lowercase token, e.g. `basketball` |
| `status` | string | see below |
| `detail` | string or null | the scoreboard's own line, e.g. `"Bot 7th"`, `"6:12 - 3rd"` |
| `period` | integer or null | quarter, inning, period or half |
| `clock` | string or null | as displayed |
| `clockSeconds` | integer or null | the same clock in seconds, for arithmetic |
| `homeScore` | integer or null | |
| `awayScore` | integer or null | |
| `stoppage` | object or null | `{ "type": …, "team": …, "since": … }` |
| `ts` | integer | milliseconds since epoch, when the state was observed |
| `snapshot` | boolean | present and `true` only on snapshot messages |

`status` is one of `SCHEDULED`, `LIVE`, `HALFTIME`, `END_PERIOD`, `DELAYED`, `SUSPENDED`, `FINAL`, `CANCELLED`, `POSTPONED`, `UNKNOWN`. Treat a status you do not recognise as `UNKNOWN` rather than discarding the message — the score and clock are still good.

## Pitfalls

**Absent means unknown, never zero.** A field the feed could not determine is omitted or null — it is never sent as `0`. This matters most for the baseball count: `balls`, `strikes` and `outs` arrive together or not at all, so a missing count must not be rendered as "0-0, 0 out". Treat `null` and absent identically.

**A quiet game is not a dead feed.** The feed publishes changes. A rain delay, a half-time break or a stoppage produces no messages at all, sometimes for many minutes. Do not use "no message recently" as a liveness check for a game — use `ping`/`pong` for the connection, and `status` for the game.

**`parentGameID` is nullable.** A pre-match game has none. Child-game routing depends on it, so handle the null case explicitly.

**Scores are integers, not strings.** Unlike some fields on the price feed, `homeScore` and `awayScore` are JSON numbers.

**Newest wins.** Compare `ts` before applying a message. Ordering is not guaranteed across a reconnect, and a snapshot can arrive alongside live frames — a frame older than the state you already hold should be discarded rather than applied.

**Do not derive the clock.** `clock` is what the scoreboard displays and only changes when the provider publishes a new value, which is roughly once per play rather than once per second. Counting down locally between messages will drift and will be wrong whenever play is stopped.
