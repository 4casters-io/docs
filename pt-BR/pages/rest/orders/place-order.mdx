Envie uma ou mais ordens. O endpoint aceita um lote — os resultados por ordem voltam em `data.createdSessions`, **posicionalmente** com o seu array `orders` de entrada. Cada entrada é ou um resultado bem-sucedido `{ matched, unmatched }` ou uma falha `{ error, errorType }`.

## Solicitação {#request}

`POST /session/v3/place`

<CodeGroup>
```bash curl
curl -X POST https://api.4casters.io/session/v3/place \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "orders": [
      {
        "gameID": "688c0516fbc14da0c202d426",
        "type": "moneyline",
        "side": "5c12bc1ce0daba000f47ba8b",
        "odds": -175,
        "bet": 100,
        "orderType": "post",
        "userReference": "docs-example"
      }
    ]
  }'
```

```json Corpo JSON
{
  "orders": [
    {
      "gameID": "4CASTER_GAME_ID",
      "type": "moneyline | spread | total | moneyline1x2",
      "side": "PARTICIPANT_ID | over | under | yes | no",
      "market": "PARTICIPANT_ID | draw",
      "odds": -110,
      "bet": 100,
      "number": 3.5,
      "orderType": "limit | post | postArb | fillAndKill | fillOrKill",
      "expirationMinutes": 10,
      "userReference": "OPTIONAL_CLIENT_SIDE_IDENTIFIER"
    }
  ]
}
```
</CodeGroup>

## Tipos de ordem {#order-types}

### `limit` {#limit}

O tipo de ordem padrão. Executa como taker contra qualquer liquidez correspondente ao seu preço ou melhor (com comissão de taker) e deixa o restante em espera no livro como maker. Uma ordem `limit` pode terminar totalmente correspondida, totalmente em espera, ou parcialmente correspondida com o restante em espera.

### `post` {#post}

Cria uma oferta em espera. Se a ordem **corresponderia** a liquidez existente ao ser enviada, o servidor a rejeita (`rejected_order_type_rules`, ex.: `"post order cannot have matches"`).

### `postArb` {#postarb}

Comporta-se como `post`, mas você pode postar **mesmo quando a ordem corresponderia**, **apenas se** suas odds americanas estiverem dentro de **1%** das odds da ordem em espera à qual você corresponderia. Se a diferença de preço for maior que 1%, o envio é rejeitado.

Exemplos:

- Melhor oferta **+100** e você posta **+100** — `post` é rejeitada (corresponderia); `postArb` é permitida.
- Melhor oferta **+200** — `postArb` a **+190** é rejeitada (longe demais de **+200**). Cerca de **+198** está no limite da faixa de 1% em relação a **+200**.
- Melhor ordem **−200** — a faixa se estende até cerca de **−202** no lado negativo (mesma regra de 1%).
- Com **+100** no livro, **−101** é o limite de referência do outro lado para a tolerância de 1%.

`postArb` evita as **taxas de taker** de uma negociação normal — você não é cobrado com taxas de taker nesse fluxo como seria se tomasse a liquidez em espera como taker.

Ordens enviadas como `postArb` são marcadas com `isPostArb: true` nas atualizações do [feed do usuário](/pt-BR/pages/streaming/user-feed) e do [feed de preços](/pt-BR/pages/streaming/price-feed); o campo é omitido para os outros tipos de ordem. A resposta do envio em si não inclui a flag.

### `fillAndKill` {#fillandkill}

Executa imediatamente como taker contra o tamanho que estiver disponível ao seu preço ou melhor, e cancela qualquer restante. Uma `fillAndKill` nunca fica em espera no livro.

Uma correspondência **parcial** é um resultado bem-sucedido: se você envia `bet: 1000` e só existem $400 de liquidez correspondível, você é correspondido em $400 e os $600 restantes são cancelados — a resposta é um sucesso, não um erro. A ordem é rejeitada (`rejected_order_type_rules`, `"fill and kill has no matches"`) apenas quando não há nenhuma liquidez correspondível. Veja os cenários de Fill And Kill nos [exemplos](#examples) abaixo.

### `fillOrKill` {#fillorkill}

Tudo ou nada. **Todo** o seu `bet` precisa corresponder imediatamente ao seu preço ou melhor, caso contrário a ordem inteira é rejeitada — incluindo as correspondências feitas pelo caminho, que são revertidas. Uma `fillOrKill` nunca fica em espera no livro, e você nunca fica parcialmente correspondido.

Use-a quando uma posição parcial é pior do que nenhuma posição, por exemplo quando a ordem é uma perna de um hedge que você só pode executar por inteiro.

As rejeições carregam `errorType: rejected_order_type_rules` com uma de duas mensagens, que distinguem "não havia nada" de "não havia o suficiente":

- `"fill or kill has no matches"` — nenhuma liquidez correspondível ao seu preço.
- `"fill or kill matched but not fully"` — parte da liquidez correspondeu, mas não o seu tamanho completo. Essas correspondências foram revertidas.

<Note>
  Um resíduo de **$10 ou menos** conta como completo: uma `fillOrKill` de $1,000 que corresponde $992 tem sucesso, porque os $8 que não puderam ser correspondidos estão abaixo do tamanho mínimo que poderia ficar em espera no livro. Um resíduo maior que $10 rejeita a ordem.
</Note>

### Cenário 5 — Fill or Kill, liquidez insuficiente {#scenario-5-fill-or-kill-not-enough-liquidity}

`fillOrKill` é a contraparte de tudo ou nada da `fillAndKill`. Onde uma `fillAndKill` de $1,000 contra $400 de liquidez corresponde $400 e cancela o resto, uma `fillOrKill` rejeita a ordem inteira e reverte esses $400 — você nunca fica parcialmente correspondido.

<CodeGroup>
```json Solicitação
{
  "orders": [
    {
      "gameID": "688c0516fbc14da0c202d426",
      "type": "moneyline",
      "side": "5c12bc1ce0daba000f47ba8b",
      "odds": -110,
      "bet": 1000,
      "orderType": "fillOrKill",
      "userReference": "docs-fillorkill-partial"
    }
  ]
}
```

```json Resposta
{
  "data": {
    "createdSessions": [
      {
        "error": "fill or kill matched but not fully",
        "errorType": "rejected_order_type_rules"
      }
    ]
  }
}
```
</CodeGroup>

Sem nenhuma liquidez correspondível, a mesma ordem é rejeitada com `"fill or kill has no matches"`.

### Cenário 6 — `postArb` vs `post` quando o livro corresponderia {#scenario-6-postarb-vs-post-when-the-book-would-match}

`post` rejeita uma ordem que corresponderia a liquidez em espera (por exemplo, melhor oferta **+100** e você tenta postar **+100**). `postArb` permite essa situação quando suas odds estão dentro de **1%** da ordem à qual você corresponderia — então o mesmo post de **+100** pode ter sucesso como `postArb`, e você evita as taxas de taker que pagaria em uma negociação normal. Se o seu preço estiver longe demais da cotação em espera (ex.: melhor oferta **+200**, mas você envia **+190**), a `postArb` é rejeitada.

<CodeGroup>
```json Solicitação
{
  "orders": [
    {
      "gameID": "688c0516fbc14da0c202d426",
      "type": "moneyline",
      "side": "5c12bc1ce0daba000f47ba8b",
      "odds": 100,
      "bet": 50,
      "orderType": "postArb",
      "userReference": "docs-postarb-same-line-as-offer"
    }
  ]
}
```
</CodeGroup>

### Cenário 7 — `moneyline1x2` (três vias no futebol) {#scenario-7-moneyline1x2-soccer-three-way}

`moneyline1x2` é o mercado de três vias do futebol — casa / visitante / empate — enviado como uma aposta yes/no sobre o resultado indicado por `market`. Abaixo, **yes no empate** a +250.

<CodeGroup>
```json Solicitação
{
  "orders": [
    {
      "gameID": "65f0c3...",
      "type": "moneyline1x2",
      "side": "yes",
      "market": "draw",
      "odds": 250,
      "bet": 50,
      "orderType": "post",
      "userReference": "docs-ml1x2-yes-draw"
    }
  ]
}
```
</CodeGroup>

Para apostar que o **time da casa não vence**, envie `side: "no"` e defina `market` como o id do participante da casa.

## Atraso ao vivo {#live-delay}

Ordens enviadas em um jogo marcado como ao vivo seguem estas regras:

1. Se a ordem não corresponde a nenhuma liquidez existente, ela é colocada imediatamente.
2. Se a ordem corresponde a liquidez existente, ela incorre em um atraso antes da execução.
3. Ligas diferentes têm períodos de atraso ao vivo diferentes:
    - **NFL, UFCMMA, NCAAF** — 3 segundos.
    - **NCAAB, NBA** — 5 segundos.
    - **ATP, WTA** — 8 segundos.
    - **Padrão** — 10 segundos.
4. Após o atraso, a ordem tenta executar:
    - Se as odds melhoram, ela corresponde instantaneamente.
    - Se as odds pioram, ela não corresponde.
