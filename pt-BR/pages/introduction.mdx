A 4casters expõe três APIs que compartilham o mesmo token de autenticação e o mesmo mecanismo subjacente de conta / livro de ofertas / liquidação. Escolha a que combina com o que você está construindo, ou combine-as — a maioria das integrações usa REST para configuração + histórico e um WebSocket para negociação ao vivo.

## Quando usar cada uma {#when-to-use-which}

| Superfície | Melhor para | Evite para |
| --- | --- | --- |
| **REST** (`https://api.4casters.io`) | Login, informações da conta, histórico de apostas, consultas, navegação de mercados, envio / edição / cancelamento em lote, qualquer coisa que você rodaria de um script ou job de backend. | Loops internos apertados em que a latência de ida e volta importa. |
| **WebSocket de ordens** (`wss://orders-api.4casters.io/orders/ws`) | Negociação ao vivo: envio + cancelamento com baixa latência, sessão persistente e correlação por `requestID`. | Leitura de estado — é um canal de escrita/comando, não uma API de consulta. |
| **WebSocket de streaming** (`wss://streaming-api.4casters.io/...`) | Ticks do livro de ofertas em tempo real (feed de preços) e eventos de correspondência / liquidação por conta (feed do usuário). | Leituras pontuais — use REST em vez de abrir um stream. |

## Autenticação {#authentication}

As três APIs compartilham um único token.

1. Chame [`POST /user/login`](/pt-BR/pages/rest/authentication) na API REST com seu nome de usuário e senha.
2. Envie o token retornado em toda requisição subsequente:
   - **REST**: cabeçalho `Authorization: Bearer <token>`.
   - **WebSockets**: cabeçalho `Authorization: <token>` no handshake.

Os tokens são válidos por 30 dias e podem ser renovados antes de expirar. Veja [Autenticação](/pt-BR/pages/rest/authentication) para renovação de token, autenticação por cookie assinado e mais detalhes.

## Convenções {#conventions}

- **Transporte**: somente HTTPS / WSS.
- **Codificação**: JSON em tudo.
- **Envelope de resposta (REST)**: `{ "data": <payload> }` em caso de sucesso; `{ "error": "<message>" }` em erros HTTP.
- **Identificadores**: ids de jogo, de participante e de ordem são strings `ObjectID` do MongoDB (hex de 24 caracteres).
- **Odds**: formato americano (negativas para favoritos, positivas para azarões), salvo indicação em contrário.
- **Tempo**: ISO 8601 com `Z` (UTC).

## Uma integração típica {#a-typical-integration}

A maioria dos clientes não triviais combina as três:

1. **REST** — `POST /user/login` uma vez, guarde o token em cache e então chame `GET /user/getMe` e `GET /games/v2/leagues` para inicializar o estado.
2. **WebSocket de streaming** — abra o feed de preços para os mercados que interessam a você e o feed do usuário para reagir às suas próprias correspondências / liquidações.
3. **WebSocket de ordens** — abra uma conexão persistente e envie / cancele ordens com baixa latência, correlacionando respostas por `requestID`.
4. **REST** — recorra a `POST /myBets/getMatchedBets`, `/myBets/getOrdersForGame`, etc. para histórico e reconciliação.
