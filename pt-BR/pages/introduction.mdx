A 4casters expõe três APIs que compartilham o mesmo token de autenticação e o mesmo motor subjacente de conta / livro de ordens / liquidação. Escolha a que corresponde ao que você está construindo, ou combine-as — a maioria das integrações usa REST para configuração e histórico e um WebSocket para trading ao vivo.

## Quando usar cada uma {#when-to-use-which}

| Canal | Ideal para | Evitar para |
| --- | --- | --- |
| **REST** (`https://api.4casters.io`) | Login, informações da conta, histórico de apostas, consultas, exploração de mercados, envio / edição / cancelamento em lote, qualquer coisa que você execute a partir de um script ou tarefa de backend. | Loops internos ajustados onde a latência de ida e volta importa. |
| **WebSocket de ordens** (`wss://orders-api.4casters.io/orders/ws`) | Trading ao vivo: envio + cancelamento de baixa latência com uma sessão persistente e correlação por `requestID`. | Leitura de estado — é um canal de escrita/comandos, não uma API de consulta. |
| **WebSocket de streaming** (`wss://streaming-api.4casters.io/...`) | Ticks do livro de ordens em tempo real (feed de preços) e eventos de preenchimento / liquidação por conta (feed de usuário). | Leituras pontuais — use REST em vez de abrir um stream. |

## Autenticação {#authentication}

**Não há chaves de API.** Você se autentica com o mesmo nome de usuário e senha que usa para entrar em 4casters.io, e as três APIs compartilham o único token que o login retorna. Chaves de API estão planejadas; consulte [Autenticação](/pt-BR/pages/authentication) para saber o estado atual.

1. Chame [`POST /user/login`](/pt-BR/pages/rest/authentication) na API REST com seu nome de usuário e senha.
2. Envie o token retornado em cada requisição seguinte:
   - **REST**: cabeçalho `Authorization: Bearer <token>`.
   - **WebSockets**: cabeçalho `Authorization: <token>` no handshake.

Os tokens são válidos por 30 dias e depois são rotacionados automaticamente. Consulte [Autenticação](/pt-BR/pages/authentication) para o tempo de vida do token, o tratamento de erros e as recomendações sobre credenciais, e a [referência de login REST](/pt-BR/pages/rest/authentication) para a forma completa da resposta.

## Convenções {#conventions}

- **Transporte**: somente HTTPS / WSS.
- **Codificação**: JSON em todos os lugares.
- **Envelope de resposta (REST)**: `{ "data": <payload> }` em caso de sucesso; `{ "error": "<message>" }` em erros HTTP.
- **Identificadores**: os ids de evento, de participante e de ordem são strings `ObjectID` do MongoDB (hex de 24 caracteres).
- **Odds**: formato americano (negativas para favoritos, positivas para azarões) salvo indicação em contrário.
- **Tempo**: ISO 8601 com `Z` (UTC).

## Uma integração típica {#a-typical-integration}

A maioria dos clientes não triviais combina as três:

1. **REST** — `POST /user/login` uma vez, guarde o token em cache e depois chame `GET /user/getMe` e `GET /games/v2/leagues` para inicializar o estado.
2. **WebSocket de streaming** — abra o feed de preços dos mercados que importam para você e o feed de usuário para reagir aos seus próprios preenchimentos / liquidações.
3. **WebSocket de ordens** — abra uma conexão persistente e envie / cancele ordens com baixa latência, correlacionando as respostas por `requestID`.
4. **REST** — recorra a `POST /myBets/getMatchedBets`, `/myBets/getOrdersForGame`, etc. para histórico e conciliação.
